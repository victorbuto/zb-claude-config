# Профиль сегмента из SML-разметки

## Что делает скилл

Описывает профиль сегмента-аудитории через **трёхстадийный анализ** размеченного датасета:
- **A** — что говорит разметка (частотности)
- **B** — что разметка упустила (перечитка текстов через линзу)
- **C** — общий профиль (перечитка без привязки к методу)

Если в папке исследования уже есть профили других сегментов того же датасета — обязательно собирает таблицу сравнения.

## Куда сохранять файлы

**Финальные отчёты** (`profile_*.md`) и HTML-сравнения — в папку исследования пользователя:
`/Users/fixed/Documents/ZB CLOUD 3600/CLOUD ZB (3600)/Researches/<project-slug>/`

Если проект новый — создать папку с осмысленным slug (например `krost-sml-segments/`, `shik-cosmetics-segments/`). Если папка уже есть для этого датасета — сохранять туда же.

**Промежуточные файлы** (`*_freq.md`, `*_compact.txt`, `*_subset.json`) — в ту же папку исследования. Скрипт `build_subset.py` принимает `--output-dir`, всегда передавать туда путь к папке исследования.

НЕ сохранять файлы в `/Users/fixed/Documents/ZB CLOUD 3600/.claude/skills/sml-segment-profile/analysis/` — это путь скилла, а не пользователя.

## Входные данные

CSV-таблица из brand-analytics-segmenter. Формат подробно — в `references/data_format.md`. Главное: текст в колонке `Текст`, разметка по методам в отдельных колонках, значения разделены `"; "`.

## Workflow

### Шаг 1. Получить путь к CSV

Если путь не дан — спросить. Если CSV большой — посмотреть структуру:

```bash
python scripts/methods_overview.py "<path_to_csv>" --top 15
```

Скрипт выводит:
- Сводку по всем методам (сколько строк размечено, сколько уник.)
- Топ-15 сегментов по каждому методу в markdown-таблицах

Эти таблицы показать пользователю — он выберет фильтр-сегмент.

### Шаг 2. Спросить фильтр и линзу

Уточнить у пользователя:
1. **Какой сегмент анализируем** — может быть один (`Социально-экономический=визажист`) или union по нескольким колонкам (`JTBD=ежедневный макияж ∪ Контекст потребления=ежедневное использование`).
2. **Через какие линзы** — один или несколько методов (Потребности, Проблемы, JTBD и т.д.).

Если разметка названия сегмента неоднозначна (например пользователь сказал «ежедневный макияж» — а в данных и `JTBD=ежедневный макияж`, и `Контекст потребления=ежедневное использование`) — предложить union и спросить.

### Шаг 3. Собрать подвыборку

```bash
python scripts/build_subset.py "<csv>" \
    --filter "Колонка=значение" \
    --filter "Колонка2=значение2" \
    --lens Потребности \
    --lens Проблемы \
    --name "Имя сегмента для файлов" \
    --output-dir "/Users/fixed/Documents/ZB CLOUD 3600/CLOUD ZB (3600)/Researches/<project-slug>/"
```

`<project-slug>` — папка под датасет (создать если нет). Например `krost-sml-segments/`.

Скрипт делает три файла:
- `<slug>_freq.md` — частотности по линзам (для Стадии A)
- `<slug>_subset.json` — JSON подвыборки
- `<slug>_compact.txt` — компактный текстовый дамп (для чтения в Стадиях B и C)

Скрипт сам предупредит если compact-файл большой — тогда читать частями.

### Шаг 4. Стадия A для каждой линзы

Содержимое `<slug>_freq.md` показать в чате. Это голые цифры из разметки. Добавить **краткий комментарий**: что бросается в глаза, какие кластеры, сравнение с другими сегментами если есть (см. шаг 7).

### Шаг 5. Стадия B для каждой линзы — перечитать тексты

Прочитать `<slug>_compact.txt` целиком. Если файл больше ~150KB — читать через Read с offset/limit (по 700 строк на чтение). Лимит чтения: 256KB / 25000 токенов.

Цель: найти **нюансы, которые разметка слила или не выделила**. Подробная инструкция — в `references/methodology.md`.

Формат вывода каждого нюанса:

```markdown
#### N. Краткий заголовок нюанса
- *«цитата из текста»* [номер записи]
- *«ещё цитата»* [номер]

Короткий вывод что это значит (1-2 предложения).
```

8-12 нюансов на линзу — оптимально.

**Критично для линзы Проблемы:** разметка проблем недополнена (5-13% строк). Стадия B вытащит реальные проблемы через перечитку. Подробнее — в `references/methodology.md`.

### Шаг 6. Стадия C — общий профиль (один раз)

Читая те же тексты **без фокуса на конкретную линзу**, собрать профиль. Структура и правила — в `references/methodology.md`. Обязательные блоки: Кто это, Главная установка, Эстетика, Подкованность, Где покупает, Архитектура брендов, Поведение, Триггеры, Боли, Язык, Социальный контекст, Главный инсайт.

Стадия C НЕ зависит от линзы — делать одну на сегмент даже если линз несколько.

### Шаг 7. Сравнение с предыдущими сегментами

Перед сохранением проверить `profile_*.md` в папке исследования (`Researches/<project-slug>/`). Если есть другие профили того же датасета — обязательно построить таблицу сравнения в конце отчёта:

| Параметр | Сегмент 1 | Сегмент 2 | Текущий |
|---|---|---|---|
| Размер | ... | ... | ... |
| Топ-потребность | ... | ... | ... |
| Главная установка | ... | ... | ... |
| Главная боль | ... | ... | ... |
| Якорный продукт | ... | ... | ... |

Если разница драматичная — подсветить как инсайт.

### Шаг 8. Сохранить отчёт

```
/Users/fixed/Documents/ZB CLOUD 3600/CLOUD ZB (3600)/Researches/<project-slug>/profile_<segment_slug>_<lens_slugs>.md
```

Содержит блоки A+B для каждой линзы, общую Стадию C, таблицу сравнения. Структура — в `assets/report_template.md`.

### Шаг 9. (Опционально) HTML-визуализация

Если пользователь просит HTML или после нескольких сегментов хочет визуально сравнить:

```bash
python scripts/generate_comparison_html.py "<csv>" \
    --segment "Визажисты:Социально-экономический=визажист" \
    --segment "Сухая кожа:Контекст потребления=сухая кожа,Контекст потребления=сухая кожа зимой" \
    --lens Потребности --lens Проблемы \
    --output analysis/comparison.html
```

Открыть через `open <file>`.

## Важные паттерны

### Что отличает хороший анализ
- Стадия B содержит **наблюдения, которых нет в разметке** — а не пересказ разметки своими словами
- Каждый нюанс подтверждён 1-2 цитатами с номерами
- В Стадии C видна **личность сегмента**, а не общие фразы про «качество и цену»
- Сравнение с другими сегментами выявляет **уникальные характеристики** текущего

### Чего избегать
- Не повторять Стадию A в Стадии B
- Не выдумывать наблюдения без цитат
- Не делать Стадию C по линзе — она про сегмент в целом
- Не пропускать сравнение если другие профили уже есть в `analysis/`

### При работе с пользователем
- НЕ показывать option menu в начале — спрашивать прямо («какой сегмент берём?»)
- После каждой линзы давать паузу — пользователь смотрит и подтверждает прежде чем переходить к следующей (если линз больше одной)
- Сохранять отчёт сразу после стадии C — не ждать одобрения
